## 1. Текущий этап

Проект находится на этапе **«Нарративный фундамент»** при сохранённом техническом прототипе карты, непрерывного времени, экспедиций, строительства, экрана героя, Dialogue Database и BattleSandbox.

Главный дизайн-приоритет остаётся прежним:

`герой → конкретные сцены нормальной жизни Дома → два варианта ремонта и причинные симптомы → стороны/условия/обычай старого соглашения → первая дальняя разведка и люди региона → главная тайна → антагонистическая сила → причинный позвоночник кампании → первый регион → ключевые NPC → первый большой квест → нарративный вертикальный срез`.

Новые крупные универсальные системы до доказательства первого региона не являются приоритетом.

### 2.1. Слияние сессионной ветки в main

Пока шла работа, пользователь параллельно открыл проект в Unity и запушил в `main` отдельный коммит (пересохранение `KingdomSurvivalDialogues.asset` реальным Unity-сериализатором). Причина обнаружена сравнением YAML через PyYAML (а не текстовым git diff, который на разных стилях сериализации не показал бы структурную суть).

При слиянии сессионной ветки в `main`:

- узел `opening` восстановлен целиком (текст + все 5 вариантов ответа) до состояния до случайной правки — с подтверждения пользователя;

- 7 новых говорящих и 20 диалогов Главы 01 из сессии добавлены поверх без изменений.

**Важно:** автоматическое `git merge` само по себе взяло бы повреждённую версию узла `opening` — сессионная ветка этот узел не касалась, поэтому Git не считал бы его «источником изменений» при трёхстороннем слиянии. Правка сделана вручную поверх результата слияния и повторно провалидирована тем же способом (PyYAML-структура + симуляция полного обхода графа Главы 01 в обеих ветках ремонта). После этого сессионная ветка запушена в `main` (`1142c2c`) обычным (не force) push — это был fast-forward относительно `origin/main`, история не переписывалась.

### 2.3. Исправление двух предсуществующих падений — 09.09.2026

По команде пользователя оба красных теста из §2.2 разобраны и исправлены. В обоих случаях причина оказалась в самих тестах, а не в проверяемом production-коде — он не менялся.

- **`BattleSandboxTests.GuardAddsFiftyPercentDefenseUntilNextActivation`** (`Expected: 16, But was: 18`). Формула защиты/урона (`SandboxCombatTagRules.GetEffectiveDefense`/`GetEffectiveAttack`, `SandboxBattle.BuildAttackPreview`) даёт для защиты 3 и атаки 5 именно 18: гвардейский бонус `floor(3 × 0.5) = 1` (минимум 1) → эффективная защита 4 → `statDifference = 1` → множитель `1 + 1 × 0.25 = 1.25` → урон `floor(15 × 1.25) = 18`. Тот же расчёт (защита 3, бонус стража 1, итог 4) независимо подтверждают 5 других, уже проходящих тестов `CombatTagModifierTests` (`Guard_UsesFiftyPercentDefenseBonusRoundedDown` и соседние) — формула самосогласована. У теста было просто неверно посчитано ожидаемое значение при написании: 16 недостижимо этой формулой ни при каком целочисленном `floor`. Исправлено: ожидание изменено на 18, добавлен комментарий с полным расчётом.
- **`DialogueDatabaseCheckSystemTests.RegenerateNarrativeIdentifiers_Creates_New_Ids_And_Remaps_Unlock_Reference`** (`NullReferenceException`). Стек-трейс в присланном `TestResults.xml` указывал на строку самого теста (сравнение `CheckId` оригинального и продублированного выбора), а не внутрь `RegenerateNarrativeIdentifiers`. Причина: `RegenerateNarrativeIdentifiers` намеренно регенерирует не только `CheckId`/`EffectExecutionId`, но и сам `ChoiceId` (см. §13 сводной инструкции, отражённый в комментарии метода) — так и задумано при дублировании узла. Тест же после регенерации искал продублированный выбор по старому `ChoiceId` («c_returnable»), которого в копии уже не существует; `FindChoiceById` возвращал `null`, обращение к `null.Check` роняло NRE. Исправлено: тест ищет соответствующий выбор в копии по позиции (индекс узла + индекс выбора внутри узла) — она не меняется при дублировании, в отличие от самих идентификаторов.

Обе правки — только в тестовых файлах (`BattleSandboxTests.cs`, `DialogueDatabaseCheckSystemTests.cs`), без затрагивания `SandboxCombatTagRules`/`SandboxBattle`/`DialogueDatabaseWindow.Editing.cs`. **Проверка Unity Test Runner не выполнялась** (в удалённой среде Unity недоступен) — статус P02-T02 переведён с «Заблокировано» на «Нужна проверка в Unity», подтверждение зелёного результата остаётся за пользователем.

### 6.2. Полностью переделан `prototype_miller`

`Assets/_Project/DialogueDatabase/Resources/DialogueDatabase/KingdomSurvivalDialogues.asset` теперь содержит не старую сцену про плотину, а **техническую «Витрину условий ответа»**. Это демонстрационный контент для автора, а не сюжетный канон и не факт мира.

В разговоре семь узлов:

1. `opening` — оглавление и инструкция по Preview;
2. `world_conditions` — флаг, знание, верхняя/нижняя граница отношения, присутствие спутника, наличие предмета;

5. `check_success` — наглядный результат успеха;
6. `check_failure` — наглядный результат провала;
7. `logic_conditions` — отдельные примеры `All`, `Any` и `Negate`.

Для всех условных ответов используется показ в неактивном состоянии с подсказкой: поэтому в Preview сразу видно, какие условия сейчас выполнены, а какие нет.

- знание: `demo_old_dam`;
- отношение: `miller:20` либо `miller:-20`;
- спутник: `demo_companion`;
- предмет: `demo_item`;
- качество: Чутьё `>= 7`;
- компетенция: Следопытство / `fieldcraft >= 3`;
- особенность: `naturalist`;

После изменения полей справа в Preview разговор нужно запускать с начала, чтобы контекст был собран заново. Для проверки трёх состояний истории проверки Preview позволяет принудительно выбрать успех или провал.
