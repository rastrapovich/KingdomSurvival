## 4. Индивидуальная кадрировка портретов говорящих — 10.09.2026

### 4.1. Что реализовано

Система портретов диалога переведена на двухуровневую модель:

1. **Общая композиция экрана** задаётся в `Kingdom Survival → UI Конструктор → Диалог → Портрет`:
   - размер и положение рамки;
   - режим изображения `Cover / Contain / Stretch`;
   - общий `Scale`;
   - общий `Offset`;
   - `Tint`;
   - `Opacity`.
2. **Индивидуальная кадрировка конкретного говорящего** хранится в `DialogueSpeakerData` и накладывается поверх общей композиции:
   - `overridePortraitFraming`;
   - `portraitScale`;
   - `portraitOffsetNormalized`;
   - `portraitFlipX`.

Если индивидуальная настройка выключена, портрет использует только общую композицию UI Конструктора. Это позволяет один раз определить дизайн диалогового экрана, а затем подправлять только проблемные портреты разных пропорций, не двигая рамку для всех персонажей.

### 4.2. Runtime

`PrototypeUIController.Narrative.cs` больше не рисует динамический портрет жёстким `ScaleMode.ScaleAndCrop`. Он получает `portrait` из `DialogueSpeakerData`, находит layout-элемент `portrait` экрана `narrative-dialogue` и передаёт всё в единый `UILayoutRuntimeApplier.ApplyDynamicImage`.

`UILayoutRuntimeApplier` теперь является единым источником математики для динамических изображений и layout-фона:

- `ResolveImageScaleMode` переводит `Cover/Contain/Stretch` в Unity `ScaleMode`;
- `ResolveImageOffset` объединяет общий pixel-offset layout и индивидуальный offset говорящего в долях фактической рамки;
- `ResolveImageScale` объединяет общий layout-scale и индивидуальный scale, включая `Flip X`;
- `ApplyDynamicImage` применяет Sprite, scale mode, tint, opacity, zoom/pan и отражение через внутренний image-layer, сохраняя clipping рамки.

Если у говорящего нет своего Sprite, layout-изображение остаётся fallback. Placeholder по-прежнему показывается, когда нет ни динамического портрета, ни пригодного fallback.

> **Уточнение (см. §10).** Описанная здесь версия `ApplyDynamicImage` рисовала динамический слой размером 100% рамки и применяла `Cover/Contain/Stretch` через `unityBackgroundScaleMode` этого же слоя — из-за этого Sprite обрезался ДО перетаскивания, и утянутые за рамку пиксели было физически невозможно вернуть назад через pan. §10 переводит этот же расчёт на модель «полное изображение + рамка-маска» без изменения публичного API/UX.

### 4.3. База диалогов: визуальное кадрирование говорящего

Добавлен `DialogueDatabaseWindow.PortraitFraming.cs`. Во вкладке говорящих теперь есть секция **«КАДРИРОВАНИЕ ПОРТРЕТА»**:

- включатель «Индивидуальная настройка»;
- масштаб от 0.05;
- числовое смещение X/Y в долях рамки;
- «Отразить по X»;
- кнопка сброса;
- preview с точными пропорциями реальной рамки экрана диалога;
- портрет можно **перетаскивать мышью прямо внутри preview**, меняя индивидуальное смещение.

Preview берёт общую рамку и настройки из UI Конструктора, поэтому автор видит сочетание общей композиции и индивидуальной поправки, а не отдельную несвязанную картинку.

`DialogueDatabaseWindow.PreviewAndSpeakers.cs` использует эту новую секцию вместо старого простого `ScaleToFit` preview. Новые говорящие создаются с нейтральными значениями кадрировки (`override=false`, scale=1, offset=0, flip=false).

### 4.4. UI Конструктор

`UILayoutEditorWindow.cs` приведён к той же математике изображения, что и runtime. Для экрана диалога preview динамического портрета учитывает:

- общий режим изображения;
- общий scale/offset/tint/opacity;
- индивидуальный scale/offset/flip выбранного говорящего.

Таким образом, UI Конструктор, База диалогов и игровой runtime больше не должны показывать три разные интерпретации одного портрета.

## 9. Свободный граф + читаемый цветовой Inspector — 10.09.2026

Реализована инструкция "свободный граф + читаемый цветовой Inspector" по её же трём обязательным приоритетам: сначала расстояние/автораскладка, затем надёжный drag ноды, затем semantic cards/colors Inspector'а. Hover-подсветка линий и прочие удобства (явно названные автором как "после этого уже можно") в этот проход не входили.

### 9.1. Приоритет 1 — автораскладка по реальным зазорам

`DialogueDatabaseWindow.Graph.cs`, `AutoLayoutDialogue`:

- фиксированная формула `60f + depth * 430f` заменена на `ComputeAutoLayoutColumnX(depth, nodeWidth) = 60f + depth * (nodeWidth + AutoLayoutHorizontalGap)` — колонка отступает от предыдущей на фактическую ширину ноды текущего режима детализации (`GetGraphNodeWidth(graphDetailMode)`) плюс `AutoLayoutHorizontalGap=220` (в требуемом диапазоне 180-240); ширина ноды одна и та же для всех нод внутри режима детализации, поэтому "ширина предыдущей колонки" — это просто ширина режима, без отдельного прохода по максимуму;
- фиксированный вертикальный шаг `60f` заменён на `AutoLayoutVerticalGap=120` (диапазон 100-140) — зазор между реальным низом одной карточки (`GetNodeWorldHeight`, уже учитывает фактическое содержимое) и верхом следующей;
- порядок узлов внутри одной колонки по вертикали раньше был порядком BFS-очереди (произвольным относительно порядка вариантов ответа у родителя). Добавлен `VisitChoiceOrderDfs` — обход в порядке массива `Choices` каждого узла (тот же `GetGraphChoiceTargets`, что и раньше, который для активной проверки уже отдаёт `successNodeId` раньше `failureNodeId`) — этот обход даёт порядок посещения, который используется только для сортировки узлов внутри колонки (глубина колонки по-прежнему считается отдельным BFS, как и раньше — кратчайшим путём, чтобы сходящиеся ветки не растягивали граф лишними колонками). Итог: первый вариант ответа родителя — самый верхний ребёнок в следующей колонке, активная проверка — успех всегда выше провала.
- узлы, не достижимые обходом от `startNodeId` (сироты), по-прежнему уходят в отдельную "orphan"-колонку за максимальной глубиной, в порядке индекса массива — как и раньше.

### 9.2. Новая команда "Раздвинуть"

Инструкция явно разделяет два действия: "Автораскладка" (полный пересчёт X/Y/порядка) и "Раздвинуть" — точечная правка тесноты без пересчёта состава и порядка. Добавлен `SpreadOutDialogueNodes`:

- ноды группируются в "колонки" по пересечению их текущих X-диапазонов (`RangesOverlap`, строгое неравенство — впритык стоящие диапазоны колонкой не считаются) — это фактическое положение на экране, а не колонка BFS-глубины;
- внутри каждой обнаруженной колонки ноды сортируются по текущему Y и раздвигаются вниз ровно настолько, чтобы зазор между соседями был не меньше `AutoLayoutVerticalGap` — X и относительный порядок никогда не меняются;
- кнопка `Раздвинуть` добавлена в `DrawGraphToolbar` между `Автораскладка` и `Центр` (порядок кнопок как в самой инструкции: `Автораскладка | Раздвинуть | Центр`).

### 9.3. Приоритет 2 — надёжный drag ноды

Раньше зона захвата для перетаскивания ноды (`dragRect`) — только маленькая иконка "⋮" (~22px по ширине до масштабирования зумом), что на уменьшенном зуме требовало высокой точности клика. Теперь `headerDragRect` — вся строка заголовка ноды по всей ширине (`headerRect.width`, высота `titleRowHeight`); иконка "⋮" (`dragIconRect`) осталась как визуальная подсказка внутри этой зоны, но не единственной кликабельной областью. Добавлен `EditorGUIUtility.AddCursorRect(headerDragRect, MouseCursor.MoveArrow)` — курсор подсказывает "здесь можно тащить" при наведении, ещё до нажатия. Тело ноды (текст, ответы) вне зоны заголовка по-прежнему не запускает drag — inline-редактирование текста (реализовано в предыдущей правке) и перетаскивание ноды остаются полностью изолированными областями клика.

### 9.4. Приоритет 3 — семантические карточки и цвета Inspector'а

`DialogueDatabaseWindow.InspectorPresentation.cs`:

- новый `SemanticCategory` enum — семь категорий: Character, Text, Check, Condition, Effect, Choice, Error;
- `GetSemanticAccentColor(category)` — тема-зависимая (`EditorGUIUtility.isProSkin`) палитра; на тёмной теме цвета светлее/менее насыщены, на светлой — темнее/насыщеннее. Condition (охра) и Effect (зелёный) намеренно контрастны — по формулировке инструкции они "визуально противоположны" (условие — то, что ПРОВЕРЯЕТСЯ, эффект — то, что МЕНЯЕТСЯ); успех/провал ответа с активной проверкой красятся как Effect/Error (зелёный/красный), а не заводят восьмую категорию ради одной пары вызовов;
- `BeginSemanticCard(title, category)`/`EndSemanticCard(category)` — карточка с тонкой (3px) акцентной полосой СЛЕВА, а не сплошной заливкой фона (инструкция: "акцентная линия, а не заливка" — сплошной цветной фон резал бы читаемость длинного литературного текста). Полоса рисуется тем же проверенным приёмом, что и `HandleGraphInspectorScrollWheel` в прошлой правке: `GUILayoutUtility.GetLastRect()` сразу после `EditorGUILayout.EndVertical()` — без риска положиться на непроверенный Rect-возвращающий overload `BeginVertical(GUIStyle, ...)`;
- `DrawSectionHeader(title, category)` — цветной вариант общего заголовка секции (используется для заголовков "УСЛОВИЯ ПОКАЗА"/"ЭФФЕКТЫ"/"ТЕКСТОВЫЕ БЛОКИ (N)"/"ОТВЕТЫ (N)");
- `GraphInspectorMinWidth` поднят с 360 до 420, `GraphInspectorDefaultWidth` — с 480 до 520 (§38): семантическим карточкам с акцентной полосой и подписанным заголовком нужно чуть больше места, чем голому `PropertyField`.

`DialogueDatabaseWindow.cs` — карточки применены везде, где раньше был голый `EditorStyles.helpBox`, без изменения состава/порядка полей внутри:

- `DrawTextBlock` → `SemanticCategory.Text`;
- `DrawChoice` → `SemanticCategory.Choice`;
- `DrawCondition`/заголовок `DrawConditionGroup` → `SemanticCategory.Condition`;

## 10. Свободное кадрирование полного портрета — 10.09.2026

Исправлена архитектурная ошибка кадрировки портретов из §4: рамка (`UILayoutElementDefinition` — размер/положение/`Cover-Contain-Stretch` из UI Конструктора) по-прежнему полностью принадлежит UI Конструктору и не меняется от персонажа к персонажу; изменился только способ ОТРИСОВКИ внутри неё.

### 10.1. Суть проблемы

Раньше `Cover/Contain/Stretch` применялись через `unityBackgroundScaleMode` (runtime) / `GUI.DrawTexture(..., ScaleMode)` (editor preview) к слою, который уже был растянут на 100% рамки. Unity сначала обрезала исходный Sprite до пропорций рамки и только потом применялся `translate`/`offset` (перетаскивание). Из-за этого уже обрезанные пиксели физически исчезали из перетаскиваемой области — потянуть портрет так, чтобы вернуть голову, ушедшую выше рамки, было невозможно: этих пикселей уже не было в отрисовываемом прямоугольнике.

### 10.2. Новая модель — Frame (маска) + Image (полное изображение)

```
PortraitFrame            (UILayoutElementDefinition — из UI Конструктора, не меняется)
    overflow: hidden
    PortraitImage         (полный Sprite целиком)
        собственные width/height (по Cover/Contain/Stretch by исходным пропорциям)
        left/top = позиция относительно рамки (общий + индивидуальный offset)
        CSS scale = только знак ±1 для Flip X (величина уже в width/height)
```

`Cover`/`Contain` теперь определяют только БАЗОВЫЙ РАЗМЕР полного изображения:

- `Cover`: `baseScale = max(frameW/sourceW, frameH/sourceH)` — картинка гарантированно перекрывает рамку по обеим осям и почти всегда шире/выше её хотя бы по одной оси;
- `Contain`: `baseScale = min(frameW/sourceW, frameH/sourceH)` — картинка вписывается целиком, может оставлять пустое поле внутри рамки;
- `Stretch`: `displaySize = frameSize` напрямую (без сохранения пропорций).

Дальше `displaySize = baseSize × индивидуальный_scale × общий_scale`, а рамка обрезает изображение исключительно через `overflow:hidden` (runtime, UI Toolkit) / `GUI.BeginGroup` (editor preview, IMGUI) — то же самое, чем рамка и раньше визуально ограничивала контент, никакого нового механизма клиппинга не добавлено. `ScaleAndCrop`/`unityBackgroundScaleMode` для этого слоя больше не используются вообще — сам слой теперь всегда рисуется `StretchToFill`/`GUI.DrawTexture(..., StretchToFill)`, потому что правильные пропорции уже заложены в его собственные `width/height`.

### 10.3. `UILayoutRuntimeApplier.cs` — общая функция расчёта

Добавлены:

- `ResolveImageRect(Vector2 sourceSize, Vector2 frameSize, UILayoutImageMode mode, float scale, Vector2 offset) → Rect` — единственная точка расчёта прямоугольника полного изображения относительно рамки. Её обязаны использовать (и используют) все три потребителя: preview Базы диалогов, preview UI Конструктора, runtime;
- `ResolveSpriteSize(Sprite sprite) → Vector2` — читает `sprite.rect`, а не `sprite.texture`, специально ради корректной работы со Sprite Atlas (§7 инструкции): Texture там — весь атлас, а не конкретный портрет.

`ResolveImageOffset`/`ResolveImageScale`/`ResolveImageScaleMode`/`ResolveImageFrameSize` не изменились по контракту (те же тесты по-прежнему проходят) — просто их результат теперь скармливается в `ResolveImageRect` вместо CSS-`translate`/`scale` поверх уже обрезанного слоя. `ResolveImageScale` продолжает возвращать `Vector3` (величина + знак для Flip), но величина (`Abs(y)`) идёт в `ResolveImageRect` как реальный размер прямоугольника, а знак (`x < 0`) — только в CSS `scale`/`GUIUtility.ScaleAroundPivot` вокруг уже готового (не примерного) центра элемента, то есть Flip не сдвигает Offset (§10 инструкции).

`ApplyDynamicImage` переписан: динамический слой теперь создаётся без стартового растяжения на 100% (`CreateSizedImageLayer` вместо `CreateImageLayer`), получает явные `left/top/width/height` из `ResolveImageRect` и рисуется `unityBackgroundScaleMode = StretchToFill`. На момент этого прохода `ApplyBackground` ещё не менялся; последующий §13 перевёл статический путь типа `Portrait` на общий `ResolveImageRect`, не меняя legacy-поведение обычного `Image`.

### 10.4. Editor preview — Base диалогов и UI Конструктор

`DialogueDatabaseWindow.PortraitFraming.cs` (`DrawPortraitTexture`) и `UILayoutEditorWindow.cs` (`DrawNarrativePortraitImage`) переведены на тот же расчёт:

1. `sourceSize` — `UILayoutRuntimeApplier.ResolveSpriteSize(sprite)` (не `texture.width/height`);
2. `imageRect = UILayoutRuntimeApplier.ResolveImageRect(...)`;
3. рамка обрезает через уже существующий `GUI.BeginGroup(frame)` (клиппинг был и раньше — раньше он просто ничего не отсекал сверх уже обрезанного `ScaleAndCrop`, если тот успевал вписать картинку внутрь group);

Перетаскивание (`HandleSpeakerPortraitDrag`) не менялось — по-прежнему двигает `portraitOffsetNormalized` как долю ширины/высоты preview-рамки; поскольку `ResolveImageOffset` домножает эту долю на фактический размер рамки, а не на размер уже обрезанного изображения, семантика offset осталась прежней, просто теперь честно применяется к полному изображению.

## 11. Контекст кадрирования: preview и runtime использовали разные размеры рамки — 10.09.2026

По скриншотам пользователя (Ульяна кадрируется крупно по грудь в preview Базы диалогов, но почти целиком — в игре) выяснилось: §10 исправил САМУ формулу кадрирования (`ResolveImageRect`), но preview Базы диалогов по-прежнему готовил для неё **другой размер рамки**, чем runtime. Схема из канона (`UI Конструктор = рамка`, `База диалогов = индивидуальный Scale/Offset/Flip`, `Runtime = пиксель-в-пиксель как редактор`) не менялась — исправлен только контекст, который preview передавал в общую формулу.

### 11.1. В чём была причина

`DrawSpeakerPortraitFraming` сам придумывал `actualResolution` для расчёта: `previewScreenScale = previewWidth(300) / portraitDefinition.Rect.width`, затем `actual = reference * previewScreenScale`. При этом `previewHeight` вычислялся ОТДЕЛЬНОЙ формулой и клэмпился в диапазон `[180, 430]`. Если реальное соотношение сторон рамки требовало высоты за пределами этого диапазона, клэмп менял соотношение сторон preview-рамки — а `ResolveImageRect` (Cover/Contain) кадрирует по-разному в зависимости именно от соотношения сторон рамки. Runtime тем временем брал реальный размер `narrativePortrait.resolvedStyle` после layout. Получались два РАЗНЫХ входа в одну и ту же (саму по себе верную) формулу.

Старый regression-тест `ResolveImageRect_SameInputs_DialoguePreviewAndRuntimeAgree` этого не ловил — он вызывал `ResolveImageRect` дважды с одинаковыми искусственными аргументами, а не сравнивал, какие аргументы реально готовят Editor Preview и Runtime.

### 11.2. Исправление

`DialogueDatabaseWindow.PortraitFraming.cs`:

- `ResolveEditorPreviewActualResolution(reference)` — новый helper, читает реальное разрешение текущего Game View через `GameView.GetSizeOfMainGameView()` (стандартный, хоть и приватный, приём Unity Editor; при недоступности — fallback на `referenceResolution`, что эквивалентно "игра запущена ровно в референсном разрешении");
- `trueFrameSize = UILayoutRuntimeApplier.ResolveImageFrameSize(portraitDefinition, reference, actual)` — **тот же метод**, которым runtime считает реальную рамку; никакой отдельной формулы для preview больше нет;
- `ResolvePreviewDisplaySize(trueFrameSize, maxWidth, maxHeight)` — новый чистый метод: равномерно (без искажения соотношения сторон) вписывает уже правильную `trueFrameSize` в разумный размер preview-панели (340×460). Это ЧИСТО визуальный zoom — никогда не участвует в математике кадрирования;
- `DrawPortraitTexture` теперь принимает `trueFrameSize` отдельно от `previewRect`: `offset`/`scale`/`imageRect` считаются в РЕАЛЬНОМ масштабе рамки (как runtime), и только готовый `imageRect` домножается на `displayScale = previewRect.width / trueFrameSize.x` перед отрисовкой — так что «что рисуем» и «во сколько раз это уменьшено для панели» разделены и не могут разойтись.

Перетаскивание (`HandleSpeakerPortraitDrag`) не менялось: оно нормализует смещение мыши как долю `previewRect.width/height`, а поскольку `previewRect` и `trueFrameSize` теперь всегда пропорциональны один другому (одним и тем же `displayScale`), эта доля математически равна доле от настоящей (true) рамки — семантика offset осталась прежней.

### 11.3. Тесты

7 новых тестов в `PortraitFramingTests.cs`: `ResolvePreviewDisplaySize` сохраняет соотношение сторон для экстремально высокой и экстремально широкой рамки (прямая регрессия старого клэмпа `[180, 430]`, который в этих же кейсах ломал бы пропорции), вписывается в границы, безопасно обрабатывает нулевую рамку; `ResolveImageFrameSize` (тот единственный метод, которым теперь пользуются и preview, и runtime) сохраняет соотношение сторон layout Rect на `1920×1080`, `1280×720` и нестандартном `2560×1080` при пропорциональном `actual`.

### 11.4. Что не проверено (честно, без Unity)

- главный сценарий пользователя (Ульяна в preview и в игре выглядит ОДИНАКОВО при одинаковых Scale/Offset) — доказан математически (preview и runtime используют один и тот же `ResolveImageFrameSize` с одним и тем же `actual`), но не подтверждён визуальным сравнением скриншотов после этой правки;

## 12. UILayout имеет окончательный приоритет над legacy min/max — 10.09.2026

После повторной ручной проверки выяснилась следующая независимая причина расхождения: editor preview уже считал правильную рамку из `UILayout`, но реальный `VisualElement` в Play Mode продолжал получать ограничения размера из старого `Prototype_Narrative.uss` после применения точного `Rect`.

Конкретно `.narrative-dialogue-portrait` всё ещё содержит legacy `max-width: 430px` и `min-height: 360px`. В текущем layout рамка `portrait` выставлена примерно в `253.5 × 131.3` reference-px. `ApplyRect` задавал эти `width/height`, но не нейтрализовал `min/max`, поэтому UI Toolkit имел право растянуть фактическую runtime-высоту минимум до 360 px. `ApplyDynamicImage` при этом продолжал рассчитывать кадрирование по размеру из `UILayout`, то есть маска и image math фактически работали с разными frame size.

Исправление сделано в одном общем месте — `UILayoutRuntimeApplier.ApplyRect`:

- перед установкой точного `left/top/width/height` вызывается `ClearLegacySizeConstraints`;
- `minWidth/minHeight` сбрасываются в `0`;
- `maxWidth/maxHeight` сбрасываются в `none`;
- визуальные свойства USS (цвет, border, alignment и т. п.) не трогаются;
- для обычных элементов generic auto-layout это влияет только при `overrideRect=true`; утверждённый позже тип `Portrait` является явным исключением и всегда применяет preset-Rect (§13); экран диалога по-прежнему применяет свой Rect собственным кодом `PrototypeUIController`.

Таким образом, когда геометрия элемента передана UI Конструктору, его Rect становится окончательным и старые USS size constraints больше не могут молча изменить runtime-рамку после cascade/layout.

### 12.1. Regression-тест

В `UILayoutDatabaseTests.cs` добавлен `ApplyRect_Clears_Legacy_MinMax_Size_Constraints`: тест создаёт `VisualElement` с legacy `minHeight=360`, `minWidth=500`, `maxWidth=430`, `maxHeight=900`, затем применяет UILayout Rect `253.5 × 131.3` и проверяет, что точные width/height сохранены, min-size обнулены, а max-size переведены в `StyleKeyword.None`.

### 12.2. Что проверено / что осталось

Статически проверено, что изменение ограничено общим `ApplyRect` и одним EditMode regression-тестом; база диалогов, сохранённые индивидуальные `Scale/Offset/Flip`, `KingdomSurvivalUILayouts.asset`, `Prototype_Narrative.uss`, Graph/Inspector и нарративный контент не менялись.

Unity Editor/компилятор в подключённой среде недоступны, поэтому новый тест здесь не запускался. После Pull нужно: дождаться чистой компиляции, прогнать EditMode `Run All`, затем открыть тот же диалог и сравнить фактическую форму рамки в Game View с UI Конструктором. Если причина устранена, runtime-портрет должен иметь тот же crop/zoom/pan, потому что и маска, и `ApplyDynamicImage` наконец используют геометрию одного размера.

## 13. Канонические preset-размеры портретов 5:7 — 10.09.2026

Утверждён и реализован базовый контракт из канона v1.29: стандартная портретная рамка больше не является произвольным `Rect`. Размер выбирается из единой таблицы reference-resolution `1920×1080`:

`XS 100×140 / S 150×210 / M 200×280 / L 300×420 / XL 400×560`.

Все пять значений строго `5:7`. Размер принадлежит месту показа, а не данным персонажа: индивидуальные `Scale / normalized Offset / Flip X` говорящего остаются отдельными и не меняются при переключении preset.

### 13.1. Единый источник размеров

### 13.2. Тип Portrait в UI Конструкторе

В `UILayoutElementKind` добавлен новый тип `Portrait` (в конец enum, поэтому числовые значения существующих типов не изменились). Для него:

- справа вместо свободного `Rect` показываются `Размер портрета: XS/S/M/L/XL`, редактируемые `X/Y` и read-only размер рамки;
- `Width/Height` вручную недоступны, resize-handle на canvas не рисуется и resize мышью не запускается;
- сам выбор типа `Portrait` считается явным применением рамки и изображения в runtime — отдельные флаги `overrideRect/overrideBackground` не нужны;
- переход из старого свободного Rect выбирает ближайший preset и сохраняет центр;
- смена preset сохраняет центр, `imageScale` и `imageOffset`; данные конкретного говорящего находятся в другом asset и также не затрагиваются;
- защитная нормализация в `OnValidate`, при сохранении и после правок не позволяет сериализованному Portrait сохранить произвольные Width/Height; старый `Stretch` для Portrait переводится в `Cover`;
- валидация базы сообщает об ошибке, если Portrait не соответствует preset или использует режим вне `Cover/Contain`.

Статическое изображение элемента типа `Portrait` и его preview переведены на тот же `UILayoutRuntimeApplier.ResolveImageRect`, что уже используют динамический портрет диалога, preview Базы диалогов и narrative-preview UI Конструктора. Теперь статический Portrait следует цепочке `полный Sprite → Cover/Contain → Scale → Offset → clip рамкой`, включая корректный размер `sprite.rect` для Sprite Atlas. `ScaleAndCrop` больше не отрезает пиксели до pan. Для обычного `Image`, который может переопределять фон без владения Rect и опираться на USS-размер, прежний путь сохранён во избежание побочной смены вёрстки.

Кнопка Reset в Базе диалогов теперь доступна независимо от состояния override и полностью возвращает индивидуальную кадрировку к `override=false`, `Scale=1`, `Offset=(0,0)`, `Flip X=false`.

## 16. Presentation-правило «одна реплика = один шаг»: DialogueChoiceKind.Continue — 10.09.2026

N05 и N06 (раздел 15) изначально собирали несколько реплик разных говорящих в один `node` — runtime строит из всех `textBlocks` узла один `NarrativeDialogueView`, поэтому рассказчик, Остафий, Лада, Мирон и Ульяна оказывались на экране одновременно. Введено новое production-правило для всей сюжетной части: **один `node` — один шаг подачи текста**; между шагами игрок нажимает нейтральное «читать дальше», настоящий выбор показывается только там, где герой действительно решает.

### 16.1. Новый вид ответа

`DialogueChoiceKind` получил пятое значение `Continue`, добавленное **в конец enum** — существующие `kind: 0..3` уже сериализованы как числа по всей базе диалогов, сдвигать их нельзя. `Continue`:

- ведёт себя в runtime как обычный переход (`TransitionTo`) — `NarrativeDialogueRuntimeSession` не потребовал изменений, кроме самого enum;
- не должен нести `successEffects`/`failureEffects` — новая проверка в `DialogueDatabaseAsset.CollectDialogueValidationIssues` сообщает об ошибке, если Continue-переход их несёт;
- в UI (`PrototypeUIController.Narrative.cs`) всегда отображается как «…», независимо от авторского текста, без вероятности/механики/tooltip, отдельным приглушённым CSS-классом `narrative-dialogue-choice-continue`;
- **не записывается в историю как «Вы: …»** — `OnNarrativeDialogueChoiceSelected` получил третий параметр `DialogueChoiceKind` и пропускает `ForPlayerChoice` для Continue.

Dialogue Database Editor обновлён: пункт «Продолжение (…)» в меню добавления ответа, отдельная подсказка и popup цели перехода в инспекторе ответа, метка «…» в Graph-карточке, «продолжение» в текстовой сводке вида ответа.
