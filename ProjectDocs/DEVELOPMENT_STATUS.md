# Kingdom Survival — Development Status

Последнее обновление: 2026-09-01

> Технический журнал фактически реализованного состояния Unity-проекта. Актуальный канон после этого этапа: `KINGDOM_SURVIVAL_GAME_CONCEPT_CANON_RU_v1_11.md`.

## 1. Текущий этап

**Автобой переведён с агрегированной силы противника на конкретный вражеский состав; после боя добавлена небольшая детерминированная ресурсная награда.**

Основное ядро сохраняется:

- один город и одна армия;
- одна активная экспедиция;
- войска экспедиции не защищают столицу;
- непрерывное время, пауза и ×1 / ×3 / ×5 / ×10;
- прямой маршрут через проходимые холмы/горы;
- после экспедиционного боя отряд остаётся на позиции;
- один сохранённый `BattleResult` используется и для прогноза, и для применения.

## 2. Что реализовано в этой итерации

### Отдельные бойцы противника

`BattleContext` теперь содержит список `BattleEnemyUnit`.

Каждая вражеская единица хранит:

- ID;
- имя;
- тип;
- максимальные HP;
- атаку;
- защиту;
- боевые теги.

Старое поле `EnemyPower` оставлено только как совместимый fallback для старого скрытого UI-кода и **не участвует в resolver как источник силы**.

### Чёрный лес

Тестовая засада теперь состоит из четырёх конкретных существ:

- два `Лесных волка` — 60 HP, атака 5, защита 2;
- `Матёрый волк` — 90 HP, атака 6, защита 4;
- `Лесная тварь` — 100 HP, атака 7, защита 5.

Теги столкновения `засада + звери` сохраняются.

Вражеские значения трёх фаз формируются из состава:

- сближение — сумма атак + ситуационные бонусы;
- столкновение — сумма средних атаки/защиты + бонусы тегов;
- удержание — сумма защит.

Для Чёрного леса базовые значения противника получаются `26 / 21 / 13`.

### Нападение на столицу

Тестовый кризис амбара теперь показывает состав:

- два налётчика;
- громила;
- грабитель.

Сила кризиса также считается из характеристик этих участников, а не из одного числа.

### Карточки врагов

Добавлен `PrototypeUIController.EnemyBattleRoster.cs`.

Он заменяет старую агрегированную карточку в текущем UI:

- в прогнозе справа показываются отдельные карточки всех врагов;
- карточка показывает имя, тип, HP, атаку и защиту;
- в результате боя справа показываются те же участники с итоговым статусом столкновения;
- карточки врагов не открывают личное окно бойца и не вмешиваются в ПКМ по нашим бойцам.

### Награда после боя

Награда входит в сохраняемый `BattleResult` и поэтому не перебрасывается при подтверждении.

Для Чёрного леса базовая добыча:

- `+4` золота отряда;
- `+2` снабжения.

По исходам:

- победа — `+4 / +2`;
- тяжёлая победа — `+3 / +1`;
- отход — `+1 / +0`;
- поражение — `+0 / +1` как минимально вынесенные остатки.

Оборона столицы:

- победа — `+2` городского золота;
- тяжёлая победа — `+1` золота;
- отход/поражение — без трофеев;
- старые потери пищи/настроения при плохом исходе сохраняются.

Добыча показывается в предбоевом прогнозе как ожидаемая и в `РЕЗУЛЬТАТЕ БОЯ` как фактически полученная; полный текст также сохраняется в `Королевских донесениях`.

### Удалён доменный автоматический возврат после боя

Так как `BattleSystem` всё равно перерабатывался, старый совместимый путь `ForceRetreat → TryOrderReturn()` удалён из применения результата. `ForceRetreat` теперь всегда `false`, что приводит доменный слой в соответствие с каноном v1.10/v1.11, а не только UI-обходом.

## 3. Что намеренно не менялось

Пока сохраняется существующая модель:

- три абстрактные фазы;
- итог определяется общей разницей очков фаз;
- травмы наших бойцов назначаются существующей системой risk/injury slots;
- враги пока не получают последовательный индивидуальный урон между фазами;
- доктрины работают как раньше.

Это отдельный минимальный этап. Следующее решение — нужно ли переходить к настоящему последовательному обмену уроном между конкретными участниками.

## 5. Проверки

К существующим 42 EditMode cases добавлены 3 проверки, поэтому после pull ожидается **45 EditMode-тестов**.

Новые проверки покрывают:

- Чёрный лес действительно содержит 4 конкретных врага с собственными характеристиками;
- очки трёх фаз противника выводятся из состава (`26 / 21 / 13`), а не из одного `EnemyPower`;
- награда экспедиционного боя входит в сохранённый результат и реально начисляется;
- существующая проверка победы столицы дополнена проверкой трофейного золота.

Дополнительно статически проверено:

- `BattleResult` хранит все ресурсные дельты до применения;
- `TryApplyPendingBattle` не выполняет повторный расчёт;
- доменный автобой больше не вызывает автоматическое возвращение экспедиции;
- новый UI использует отдельные классы `battle-enemy-unit-card` и не конфликтует с обработчиком личных карточек наших бойцов.

В текущем окружении нет Unity Editor, `dotnet`, `csc` или `mcs`, поэтому финальная компиляция и NUnit выполняются после pull в Unity.

## 6. Что проверить после pull

1. Открыть проект; Console должна быть без compile errors.
2. Запустить EditMode Test Runner; ожидается `45/45`.
3. Добраться до Чёрного леса: справа должны быть четыре отдельные карточки врагов вместо одной карточки `Сила N`.
4. Проверить значения: два волка, матёрый волк, лесная тварь; у каждого видны HP/атака/защита.
5. Переключить три доктрины: прогноз должен пересчитываться, состав врага — оставаться тем же.
6. Провести бой и проверить `РЕЗУЛЬТАТ БОЯ`: справа остаются карточки участвовавших врагов с итоговым статусом.
7. Проверить выдачу добычи Чёрного леса и её совпадение с прогнозом.
8. Через DEBUG вызвать нападение на столицу: справа должны быть четыре отдельных нападающих.
9. При успешной защите проверить `+2` либо `+1` городского золота согласно исходу; при плохом исходе трофеев быть не должно.
10. Перепроверить, что после экспедиционного боя отряд не возвращается автоматически и ждёт нового приказа.
11. Коротко проверить регрессии: ПКМ карточек наших бойцов, drag-and-drop, рельеф без мерцания, маршруты, исследования, ягоды, снабжение и автопауза.

## 7. Следующий рекомендуемый этап

После проверки этой версии оценить не внешний вид, а ощущение от расчёта. Если отдельные враги уже читаются лучше, но итог всё ещё кажется искусственным, следующим этапом заменить `общая сумма фаз → injury slots` на последовательный детерминированный обмен конкретным уроном между участниками.
